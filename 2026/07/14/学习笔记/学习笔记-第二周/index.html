学习笔记——RAG检索增强

为什么需要 RAG

大语言模型（LLM）虽然强大，但存在几个固有的局限：

  • 知识截止（Knowledge Cutoff）：模型只掌握训练数据截止时间之前的知识，无法回答之后发生的事情。
  • 幻觉（Hallucination）：当模型缺乏相关知识时，仍会”自信”地编造看似合理但错误的内容。
  • 私有数据缺失：模型无法访问企业内部文档、个人笔记等私有知识。
  • 可溯源性差：难以判断答案的依据来自哪里，缺乏引用来源。

RAG（Retrieval-Augmented Generation，检索增强生成） 的核心思想是：在让模型生成答案之前，先从外部知识库中检索出相关的资料，再把这些资料作为上下文拼接进提示词（Prompt），让模型基于真实资料来生成回答。

这样做的好处是：

  • 无需重新训练模型即可注入新知识；
  • 显著降低幻觉，答案有据可查；
  • 支持引用来源，可溯源、可验证；
  • 更新知识只需更新知识库，成本远低于微调。

一句话概括：RAG = 检索（Retrieval）+ 生成（Generation），用”开卷考试”代替”闭卷考试”。

RAG 的整体流程

一个典型的 RAG 系统可以拆分为两大阶段：离线索引（Indexing） 与 在线检索生成（Retrieval & Generation）。

这里的”离线”与”在线”，指的是两个阶段发生的时机不同、是否由用户的实时提问触发，而非字面意义上的”断网 / 联网”：

  • 离线（Offline）：在用户提问之前就完成的准备工作，是一次性或定期批量执行的。它不受用户请求触发，可以放在服务器空闲时（比如半夜）慢慢跑；即使耗时长、计算量大也不影响用户体验。只有当知识库更新时，才需要重新执行（增量或全量）。
  • 在线（Online）：由用户的每一次提问即时触发，处于请求的关键路径上，对延迟敏感——用户正等着结果，因此必须快速完成，并且每次提问都要重新走一遍。

之所以把二者拆开，正是为了把耗时的向量化与索引构建挪出用户请求路径，让在线响应尽可能快。可以类比”开卷考试”：离线阶段相当于考前把书本整理好、贴好标签、编好目录；在线阶段则是考试时根据题目快速翻到相关页、组织出答案。

索引阶段（离线）

  1. 加载（Load）：从各种数据源（PDF、Markdown、网页、数据库等）读取原始文档。
  2. 切分（Chunk / Split）：将长文档切分为若干较小的文本块（Chunk）。
  3. 嵌入（Embed）：用嵌入模型（Embedding Model）把每个文本块转换成向量。
  4. 存储（Store）：把向量及其对应的原文存入向量数据库，建立索引。

检索生成阶段（在线）

  1. 查询嵌入：把用户问题用同一个嵌入模型转成向量。
  2. 相似度检索：在向量库中找出与问题向量最相似的 Top-K 个文本块。
  3. （可选）重排序：用更精细的模型对候选结果重新排序。
  4. 构造提示词：把检索到的文本块与用户问题拼接成 Prompt。
  5. 生成回答：LLM 基于上下文生成最终答案，并可附带引用来源。

文档切分（Chunking）

切分是 RAG 中最容易被忽视、却对效果影响巨大的一步。切得太大，检索精度下降、噪声增多、还可能超出上下文窗口；切得太小，则可能割裂语义、丢失上下文。

常见的切分策略：

  • 固定长度切分：按固定字符数或 Token 数切分，实现简单但可能从句子中间截断。
  • 按分隔符切分：按段落、句子、标题等自然边界切分，保留语义完整性。
  • 递归切分（Recursive）：按优先级依次尝试多种分隔符（段落 → 句子 → 词），是实践中最常用的策略。
  • 语义切分（Semantic）：根据句子之间的语义相似度来决定切分点，让语义相近的内容留在同一块中。

一个常见的技巧是设置 重叠（Overlap）：让相邻文本块之间保留一部分重复内容，避免关键信息恰好被切分点分割。

# 使用 LangChain 的递归切分器示例
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,       # 每块最大字符数
    chunk_overlap=50,     # 相邻块的重叠字符数
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],
)
chunks = splitter.split_text(document_text)

嵌入与向量数据库

文本嵌入（Embedding）

嵌入是把文本映射到高维向量空间的过程，使得语义相近的文本在向量空间中距离也相近。这是 RAG 能够进行”语义检索”而非简单”关键词匹配”的基础。

衡量两个向量相似度最常用的是余弦相似度（Cosine Similarity）：

$$
\text{sim}(A, B) = \frac{A \cdot B}{|A| |B|} = \frac{\sum_{i=1}^{n} A_i B_i}{\sqrt{\sum_{i=1}^{n} A_i^2} \sqrt{\sum_{i=1}^{n} B_i^2}}
$$

余弦相似度取值范围为 $[-1, 1]$，越接近 1 表示两个向量方向越一致、语义越相近。

向量数据库

向量数据库专门用于存储海量向量并进行高效的相似度检索。当数据量很大时，逐一计算相似度（暴力搜索）成本太高，因此普遍采用近似最近邻（ANN, Approximate Nearest Neighbor） 算法，如 HNSW、IVF 等，在检索速度与精度之间取得平衡。

常见的向量数据库：Milvus、Qdrant、Weaviate、Chroma、Pinecone、FAISS（严格说是检索库）等。

检索与重排序

检索策略

  • 稠密检索（Dense Retrieval）：基于向量语义相似度，擅长理解语义、处理同义表达。
  • 稀疏检索（Sparse Retrieval）：基于关键词匹配（如 BM25），擅长精确命中术语、专有名词。
  • 混合检索（Hybrid Search）：结合稠密与稀疏检索的结果，兼顾语义与关键词，往往效果最好。

重排序（Rerank）

初步检索追求的是”召回”，即尽量把可能相关的文档都捞出来，因此速度快但精度有限。重排序则在候选集上使用更精细（但更慢）的 Cross-Encoder 模型，对”问题—文档”对逐一打分并重新排序，从而把最相关的内容排到最前面。

检索器（Bi-Encoder）分别编码问题和文档，速度快；重排序器（Cross-Encoder）把问题和文档拼在一起编码，精度高但慢。二者配合是”先粗筛、后精排”的典型思路。

生成阶段

检索到高质量的上下文后，需要把它们组织进提示词。一个良好的 RAG 提示词通常包含：

  • 角色与任务说明：告诉模型它的职责。
  • 检索到的上下文：作为回答的依据。
  • 明确的约束：例如”只根据提供的资料回答，若资料中没有则回答’不知道’”，以进一步抑制幻觉。
  • 用户问题。
你是一个知识问答助手。请只根据下面提供的【参考资料】回答用户的问题。
如果参考资料中没有相关信息，请直接回答"根据现有资料无法回答"，不要编造。

【参考资料】
{retrieved_chunks}

【用户问题】
{question}

进阶优化技巧

基础 RAG（Naive RAG）在真实场景中常会遇到检索不准、上下文不足等问题，业界发展出许多优化手段：

  • 查询改写（Query Rewriting）：把口语化、模糊的问题改写成更适合检索的形式。
  • 查询扩展 / 多查询（Multi-Query）：从一个问题生成多个不同角度的子查询，分别检索后合并结果，提高召回。
  • HyDE（Hypothetical Document Embeddings）：先让 LLM 生成一个”假设答案”，再用这个假设答案去检索，往往比原问题更贴近目标文档。
  • 父子块检索（Parent-Child / Small-to-Big）：用小块做精准检索，命中后返回其所在的大块作为上下文，兼顾精度与完整性。
  • 元数据过滤（Metadata Filtering）：结合时间、来源、标签等元数据缩小检索范围。
  • 上下文压缩（Contextual Compression）：对检索结果做提炼，去除无关内容，节省上下文窗口。

此外还有 GraphRAG（基于知识图谱）、Agentic RAG（让 Agent 自主决定是否检索、检索什么、检索几次）等更前沿的方向。

评估（Evaluation）

RAG 系统的效果评估通常从检索质量和生成质量两个维度进行，常用指标包括：

  • 上下文相关性（Context Relevance）：检索到的内容是否与问题相关。
  • 忠实度（Faithfulness）：答案是否忠实于检索到的上下文，有没有编造。
  • 答案相关性（Answer Relevance）：答案是否切实回答了用户的问题。
  • 召回率 / 精确率：检索层面是否找全、找准了相关文档。

RAGAS、TruLens 等工具提供了自动化的 RAG 评估能力。

小结

RAG 通过”先检索、再生成”的方式，为大语言模型接入了外部与私有知识，有效缓解了知识截止与幻觉问题，且成本远低于微调。它的效果取决于每一个环节——切分是否合理、嵌入是否准确、检索是否精准、重排是否得当、提示是否清晰。理解并逐环节优化这条链路，是构建高质量知识问答系统的关键。
